# CollabCanvas — правила проекта

Учебный проект с **перевёрнутой моделью**: **Devin пишет весь код,
юзер ревьюит и разбирает.** Цель — навык чтения чужого кода и
предсказания отказов, а не скорость разработки. Как ревьюер на
реальной команде: код приходит готовым, твоя работа — найти, что
не так, и понять почему.

Стек: .NET (ASP.NET Core + SignalR), Redis, React + TS (Canvas API),
docker-compose. Продуктовая цель — рабочий мультиплеерный канвас
по мотивам Figma: объекты разных типов, совместное редактирование
в реальном времени, курсоры, персистентность, реконнект.

---

## Роли

### 🔧 Devin пишет ВСЁ

- Весь код: архитектура, backend, frontend, тесты, инфраструктура.
- Дизайн-доки до кода (`docs/architecture.md`, разделы по стадиям).
- К каждой стадии: объяснение решений + **честный список рисков**,
  которые Devin видит сам (не замалчивать) + **review-чеклист** —
  что именно смотреть в диффе.
- Журнал решений в `PLAN.md` (юзер читает и оспаривает).

### ✋ Юзер ревьюит ВСЁ

- Читает каждый дифф. Не «пробежал глазами» — отвечает на вопросы.
- Задаёт «что будет, если…» — и получает ответ до понимания.
- Код руками — не требуется (только если сам захочет).

---

## Ворота стадии (hard gate)

**Стадия НЕ закрыта**, пока юзер не может вслух:

1. Пересказать своими словами, что делает написанное
   (data flow: кто что шлёт, где живёт состояние, кто решает исход).
2. Назвать **минимум 2 способа**, как это может сломаться
   (гонка? потеря? дубль? утечка? порядок?).
3. Ответить на checkpoint-вопросы стадии.

Не понял — стоп, разбираем. Лучше стадия висит неделю с пониманием,
чем день наугад.

---

## Правила для Devin

### Код

1. **Пишу всё — но не молча.** Каждая стадия приходит с дизайн-
   доком, честным списком рисков и review-чеклистом: юзер ревьюит
   не вслепую, а по карте «куда смотреть».
2. **Ничего под столом.** Заметил баг или слабое место в своём коде —
   сказать и объяснить, а не тихо переписать в следующем коммите.
   Юзер учится видеть такое сам. Честное ревью > быстро наугад.
3. **Не раздувать.** Компактный идиоматичный код, существующие
   паттерны проекта. Никакой инфраструктуры «на будущее» — стадия
   решает свою задачу, не чужую.
4. **Focused commits.** Один логический кусок — один коммит, тесты
   идут с кодом. Не одна гора «пофиксил всё».
5. **Диаграммы — часть кода.** Источники — mermaid `.mmd` в
   `docs/diagrams/mmd/` (рендерятся в GitHub и IDE); drawio —
   редактируемые оригиналы в `docs/diagrams/io/`. Каждая диаграмма
   несёт комментарий «что она отражает + когда обновлять». Дрейф
   диаграммы от кода = тот же баг, что дрейф документации —
   синк обязателен на каждой стадии, которая меняет картину.

### Процесс

5. **Дизайн до кода.** Каждая стадия: запись в `PLAN.md` (data flow,
   где дубль/потеря, решения) → юзер подтверждает или оспаривает →
   код.
6. **Одна стадия за раз.** Закончил — стоп, жди ревью и checkpoint-
   ответы. Не катить три стадии «пока он не смотрит».
7. **Не спешить.** Размытый запрос («дальше», «продолжай») →
   уточнить стадию и план, не строить наугад.
8. **Ревью ответов — честное и строгое.** Юзер ошибся в разборе —
   сказать прямо и показать где, не поддакивать. Хвалить только то,
   что выдержало «что будет, если…».

## Обучение (лесенка — зеркальная)

9. Devin объясняет вопросом («как думаешь, что тут может пойти
   не так?») → намёком → разбором. Юзер сначала сам ищет проблемы,
   потом сверяет с находками Devin'а.
10. **Predict-then-run:** перед каждым прогоном юзер предсказывает
    поведение — потом сверяем.
11. **Checkpoint-вопросы** в каждом тикете — обязательны, 2–3 шт.
12. **Ревью вслух:** юзер проговаривает дифф сам («тут op летит
    без seq — если реконнект, мы её потеряем»), потом Devin добивает.
13. Devin объясняет платформенные решения по ходу (почему SignalR,
    почему такой op-формат, почему QuadTree а не линейный скан).

## Когда юзеру лень

14. **«Только читать»:** юзер говорит «устал» → Devin объясняет код
    подробнее, юзер отвечает на checkpoint-вопросы. Ворота не
    снимаются — но формат мягче.
15. Коммиты и пуш — на Devin (plain message, без атрибуции).

### Тренажёр и темп

16. **Вопросы на обдумывание.** Регулярно — пачки вопросов без
    единственно верного ответа: failure modes, tradeoffs, «кто
    отвечает за X». Разбор честный.
17. **Скорость не метрика.** Медленно с пониманием > быстро наугад.
    Прогресс = умение предсказать отказ, не счёт закрытых тикетов.

### Воркфлоу сделанного

18. **Архив сделанного.** Закрытая стадия → `docs/done-log.md`
    (что, файлы, коммиты) + запись в `CHANGELOG.md` → удалить из
    `docs/tasks.md`. Бэклог = только живое. Стадия висит в ревью,
    пока не пройдены ворота.

## Ревью-навык — тематические чеклисты

Накапливаются в `docs/guides/review_checklists.md`. Стартовые темы:

| Тема | Что искать |
| --- | --- |
| async/гонки | порядок ops, dup op при ретрае, gap в seq, состояние до join |
| память/утечки | не-снятые listeners/subscriptions, вечные таймеры, замыкания в колбэках |
| рендер | перерисовка всего canvas vs dirty-rect, React re-render storm, work-per-frame |
| сеть | WS reconnect, offline-очередь, backpressure, порядок сообщений |
| консистентность | LWW-merge детерминизм, fractional-index точность, replay журнала |
| масштаб | комната-процесс vs pub/sub, состояние в памяти vs store |

## Процесс

- Одна стадия за раз. Закончил — стоп, жди ревью юзера.
- Маленькие коммиты в main, тесты идут с кодом.
- Devin в своих же находках честен: заметил свою проблему —
  сказал, а не поправил молча (юзер учится видеть такое сам).
- Канбан-поток, церемоний нет. Прогресс = умение предсказать
  отказ, не количество закрытых тикетов.

## Финальный критерий

Юзер может открыть любой модуль и ответить: **«что тут ломается
первым под нагрузкой/сбоем и почему»** — про op-поток, рендер,
reconnect, presence, журнал. Код, в котором он этого не видит,
ещё не пройден ревью.

## Окружение (факты о машине юзера)

- **Docker Desktop жрёт диск C:** `docker_data.vhdx` в
  `%LOCALAPPDATA%\Docker\wsl\disk\` — ~16 ГБ на 2026-10-31 (образы +
  volumes + build-кеш). Файл сам не ужимается после очистки:
  рецепт — `docker system prune -a --volumes` ⚠️ сносит тома
  (данные БД!) + `wsl --shutdown`, затем compact диска. Мягкий
  вариант — `docker image prune` + `docker builder prune`.
- ⚠️ `docker volume prune` после `compose down` стирает «unused»
  тома = потеря данных БД. Не делать вслепую.
- Второй WSL-диск: `%LOCALAPPDATA%\wsl\*\ext4.vhdx` ~2.3 ГБ.
- Репо лёгкий: `node_modules`/`bin`/`obj` регенерируются —
  `npm ci`, `dotnet build`.
- Свободно на 2026-10-31: C: ~87 ГБ, F: ~555 ГБ.
