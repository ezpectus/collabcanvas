# Auth + роли по ссылке — дизайн для ревью (НЕ реализация)

Решение юзера зафиксировано: **как в Canva** — аккаунт у каждого,
доки висят на акке владельца, ссылка несёт роль. Этот файл — план
и карта взломов до кода. Подтверди или оспорь → потом T-26 в работу.

## Роли (по возрастанию прав)

| Роль | Может | Нельзя |
|---|---|---|
| **owner** | всё + удалить/делистить док + выдать/отозвать ссылки | — |
| **admin** | edit + управлять ссылками + кикать редакторов | удалить док |
| **user** (editor) | весь op-поток: create/patch/reorder/undo | unlist, ссылки |
| **viewer** | join, presence курсор, читать всё | ЛЮБОЙ op (сервер режет) |

## Модель аккаунтов — минимальная, не своя крипта

- Таблица `users(id, login, pass_hash, created)` — argon2/bcrypt,
  НЕ SHA256+salt самописный (классика взлома).
- Сессия = подписанный cookie или bearer-токен на join.
  SignalR-joint принимает `?access_token=` или header.
- Анонимный viewer — спорный момент: Canva требует акк для edit,
  view по ссылке бывает гостевым. **Решить:** гость-viewer или нет.

## Ссылка = грант роли, не секрет идентичности

- Док хранит набор ссылок: `{ token, role, createdBy, revoked }`.
  URL вида `?doc=X&invite=<token>`.
- Открываешь ссылку → если в акке нет членства, токен зачисляет
  роль (viewer/editor — что выбрал шарящий). owner/admin —
  только прямым инвайтом на login, НЕ по ссылке (иначе линк =
  ключ от дока в обход всего).
- Отзыв: `revoked=true` → следующий join отказан. Существующие
  соединения — выкинуть при следующем op (fail-close на мутации).

## Где enforce — СЕРВЕР, не клиент

Клиент прячет кнопки для вежливости, но решение принимает:

1. `DocumentHub.Join` — проверка членства/токена → role.
2. Каждый входящий op: `role >= user` или drop+error. **Без этого
   вся система — косметика:** viewer открывает devtools и шлёт Patch.
3. `DELETE /docs/{id}` → owner only. `/docs` список — только
   доки вызывающего (сейчас возвращает ВСЕ — утечка существования).
4. `/ops` tail — viewer+ (не аноним: журнал = история правок).
5. Rate-limit и валидация уже есть — остаются, роль не ослабляет.

## Threat-model — что ломается сейчас и после

**Сейчас (голое):** любой id = бог. `/docs` перечисляет все доки
(перебор не нужен — список открыт), unlist кем угодно, /ops чужой
журнал, rate-limit per-connection (обходится вторым сокетом).

**После auth — типовые взломы, которые надо проверить тестами:**
- Подбор doc-id/invite-token → токены 128бит+, не угадываемые.
- Забытый эндпоинт: /ops, /docs, unlist, presence — каждый
  проверить на viewer-роль, НЕ только op-поток.
- Escalation: viewer шлёт Reorder/Patch — отказ; member меняет
  свою роль Patch'ем документа? Роли живут ВНЕ документа (отдельная
  таблица) — иначе LWW-патч = повышение прав.
- Отозванная ссылка но живой сокет — enforce на мутации.
- Session-fixation / reuse чужого токена — bind к user.id.
- XSS: text-пропы рисуются на canvas (не DOM) — безопасно;
  doc-id в innerHTML нигде не идёт. Проверить layers/history панели.
- Pass: минимальная длина + троттлинг логина (та же rate-limit).

## Группировка — ПО ТЕГАМ (решение принято)

- `group` — обычный prop-строка (id группы) на объекте. НЕ дерево
  parent-child: плоский тег = LWW-бесплатно, нет циклов, нет
  каскадов удаления.
- Семантика: клик по члену группы выбирает ВСЕХ с тем же тегом
  (расширение hit-test → выделение группы). Трансформ уже умеет
  multi-select — группа = сохранённый multi-select.
- `ctrl+g` группирует выделение (новый group-id), `ctrl+shift+g`
  разгруппировывает (снять тег). Ungroup = Patch, undo-aware.
- Края честно: вложенных групп нет (тег один — Figma-вложенность
  это уже дерево, отказ сознательный); lock и группа ортогональны.

## Отложено — с причиной и триггером возврата

| Что | Почему сейчас нет | Когда возвращаться |
|---|---|---|
| co-typing | операционная модель (OT/CRDT-char) = отдельный проект сложности | после auth; whole-string LWW честно держит демо |
| mobile/touch | pointer-слой + pinch + long-press, отдельный QA-цикл | когда desktop-ревью пройдено |
| scale-hardening | fencing/join-cache/inc-index — нет нагрузки, чинить нечего | реальный второй инстанс под нагрузкой |
| comments | привязка к объектам + рассылка — без auth бессмысленно | после auth |
| rulers | ниша, не блокирует ничего | по запросу |

## Порядок внедрения auth (этапами, каждый — свой тикет)

1. **users + session** — регистрация/логин, cookie, без ролей
   (все залогиненные = editor как сейчас). Миграция: анонимные
   доки получают owner = NULL → первый залогиненный забирает?
   НЕТ — честно: старые доки остаются открытыми (legacy-режим).
2. **doc.members + roles** — join проверяет, мутации режутся.
3. **invite-links** — выдача/отзыв owner/admin.
4. **UI** — login-экран, role-бейдж, share-диалог, скрытие
   недоступных кнопок (только косметика — enforce на сервере).

Каждый этап — коммит+тесты. Бот получит viewer-клиента и
проверит, что его ops отброшены (тест на enforce, не на косметику).

## Stage 1 — статус (закоммичено 9d4f56d + fd6eaca, в `review`)

Реализовано: `user:{login}`+`sess:{token}` в Redis (TTL 7d sliding,
revocable — JWT осознанно не взят: серверный токен отзывается
DELETE'ом, self-signed JWT нет). BCrypt wf11 (~60-80мс/верификация).
Эндпоинты register/login/me/logout, uniform 401 (нет enumeration).
Токен в hub: `access_token` query ИЛИ Authorization-header — SignalR-
браузер шлёт query (WS не умеет хедеры), Node-клиент шлёт header;
берём оба, иначе теряем тестовый бот или браузер.
Presence-имя = серверный логин (self-claimed перезаписывается —
проверено ботом с name:'hacker' → комната видит login).

Принятые отступления от дизайна выше:
- cookie → Bearer-токен в localStorage: проще, но читаем XSS —
  записано в дыры T-26; httpOnly-cookie потребует CSRF-слоя.
- Гость остаётся editor ДО stage 2 (legacy-режим, осознанно —
  иначе флип роли ломал бы все существующие тесты бота).

Дыры, записанные для stage 2+ (не молчим): /docs открыт · logout
не рвёт живой сокет (resolved uid кэширован в Context.Items —
нужен per-op пересмотр или versioned session) · /auth/login без
throttle · токен в WS query → access-логи прокси · пароль без
max-длины (bcrypt режет >72B молча).

## Stage 2 — статус (закоммичено 875b916 + 5e242dd, в `review`)

Реализовано: `doc:{id}:members` (hash login→role), `user:{login}:docs`,
`owned:docs`. Роли owner/admin/editor/viewer вне документа —
Patch не может отчеканить право. Owned-док = только POST /docs
авторизованным (создатель=owner). Implicit-join unowned-дока —
legacy-open: **first-claim отклонён**, логин не крадёт чужой
анонимный док (осознанный компромисс: unowned-доки открыты всегда,
owned — закрыты с момента создания).

Enforce-точки: JoinDocument (HubException → invoke reject),
SubmitOp per-op (revoke на следующем op — живой сокет не спасает,
закрывает дыру stage-1 «logout не рвёт сокет» для членства),
Presence gated, /docs фильтр (member∪unowned / guest=unowned),
DELETE+/ops role-gated, members CRUD (admin: editor/viewer; owner
нельзя отчеканить через members — 400; admin не сажает admin — 403).

Бот +18 authz-чеков, живьём на compose. Поймано 2 краша на живом
прогоне (записано в CHANGELOG): Results.Forbid() требует ASP.NET
auth-пайплайна; TryParse на DI-типе ломает minimal-API биндинг.

Открытые края stage 2 (честно): per-op check = 1-2 Redis-чтения на
op — без кэша сознательно (кэш = окно revocation; профилировать
на реальной нагрузке) · EffectiveRole на HubException — текст
'forbidden' доезжает в e.message обёрнутым · guest-presence на
owned-доке молча дропается · членство по login, не uid — rename
аккаунта (фичи нет) потребует переноса · viewer видит курсоры
(presence read-only по природе).
